# DeepSeek 压缩缓存，Cursor 开始接手长期项目

Juju Radar · 2026.09.11

<!-- reading-stats -->约 3,200 字 · 阅读约 11 分钟<!-- /reading-stats -->

一个 Agent 连续工作几天，麻烦不只在于模型够不够聪明。反复读文件要花钱，上下文要保存，多个任务还得有人协调。昨天，DeepSeek、Cursor 和 OpenAI 分别拿出了更具体的解决办法。

本期还看三项不同方向的进展：可以边听边说的语音 API、让视觉语言模型直接选择机器人动作的接口，以及一篇把游戏规则与画面生成分开处理的论文。

## 🧠 DeepSeek V4.1 Flash：长任务先从缓存省起

基础模型 / 推理基础设施 · **9.5/10｜建议深挖**

DeepSeek 于 9 月 10 日正式发布 V4.1 Flash，支持原生图像理解和百万 token 上下文。它采用输入、输出不对称的因果编码器—解码器结构：读入内容时每个 token 激活约 8B 参数，生成内容时激活约 16B。Agent 经常一次读入很多工具结果、只输出一小段操作，这种设计针对的正是输入远多于输出的工作负载。

更值得细读的是 **KV Cache，也就是模型为了复用前文计算而保存的缓存**。新模型让不同层复用缓存，并采用 FP4 精度存储；在相同序列长度下，全局 KV 缓存降到每 token 890 字节，约为 V4 Flash 的四分之一。另一项部署优化只重放最近一段内容来恢复局部状态，使需要持久保存到 SSD 或主机内存的 KV 缓存约降到八分之一。这两个比例对应不同缓存，不能理解成整套服务显存和费用都按同样比例下降。

权重、推理文件和技术报告已公开，API 也已切换。部署时要留意：552B 是主干参数，另外还有 196B 的 Engram 条件记忆等组件；8B/16B 是每个 token 的激活量，并不意味着普通显卡就能装下模型。官方列出的代码任务成绩有明显进步，但框架、推理预算和测试集版本会影响结果。技术报告也承认，最难的推理任务仍与领先闭源模型有差距，缓存近似恢复的极端情况还需继续检查。

对现有 API 用户还有一件实际的事：官方计划在北京时间 **9 月 14 日 12:00 后，将 V4 Pro 请求路由到 V4.1 Flash**，直至后续 Pro 上线。依赖旧模型行为的应用，应先做自己的任务回归测试，而不只比较排行榜。

## 🛠️ Cursor Projects：把几个月的工作留在同一个项目里

Coding Agent / 产品 · **9/10｜建议深挖**

Cursor 在 9 月 10 日推出 Projects 测试版，并开始向用户逐步开放。用户面对的是一个协调 Agent：它负责拆任务、派活和汇总，不亲自写代码。子 Agent 可以在云端工作，需要本机测试时再调用本地 Agent；项目通过共享文件积累代码库知识、测试方法和工作偏好，也可以订阅 PR、消息或定时信号。

这个设计处理的是日常开发中很具体的断层：一次聊天结束后，后续迁移、修复和维护常常要重新交代背景。Projects 尝试让同一份上下文伴随整个工程持续更新。Cursor 称内部已用它推进数百个 PR 的迁移，也用它维护设计系统；因此，它比“同时开几个聊天窗口”多出的核心能力，是持续保存经验并在新事件发生时继续工作。

官方提到可向数千个子 Agent 分派任务，并称使用者合并了更多 PR。这些是公司的使用数据，并非随机对照实验；PR 数量也不等于软件质量或净节省工时。判断长期项目有没有做好，仍要看返工、回归故障和维护成本。当前是逐步开放的测试版，不能假定每个账号已经可用。

[Cursor Projects 发布说明](https://cursor.com/blog/projects)

## ☁️ OpenAI Agents API：把 Codex 的运行框架交给开发者

Agent / 开发基础设施 · **9/10｜建议深挖**

同一天，OpenAI 发布 Agents API 公测版。开发者除了指定模型和工具，还能选择 Agent 的执行环境：OpenAI 托管沙箱、自有基础设施，或合作方沙箱。负责组织模型调用、工具和上下文的 Codex 运行框架，则由 OpenAI 维护。

这里打包了不少过去需要应用团队自己补的工程能力：长会话的上下文压缩、按需寻找工具、用程序组合工具调用，以及子 Agent 协作。它降低了从“模型能调用一个函数”到“任务能连续执行并留下文件”的搭建成本，也让运行框架的版本和升级方式成为开发者需要关注的依赖。

官方称 API 本身不额外收费，按实际使用的 token 和工具计费；这不等于长期任务免费。客户证言中的延迟和成本改善没有统一实验条件，暂不作为通用收益估计。对于涉及真实业务的 Agent，任务权限、失败后的恢复方式和验收标准，仍需由应用方明确。

[Agents API 公测说明](https://openai.com/index/introducing-the-agents-api/)

## 🎙️ GPT-Live-1：一边说话，也能听见你改主意

语音 / 多模态交互 · **8.5/10｜持续观察**

GPT-Live-1 此前已用于 ChatGPT，9 月 10 日的新进展是向 API 开发者开放。它采用全双工交互，可以同时处理传入和传出的声音；更复杂的推理和工具操作，则交给后台文本模型。用户打断、更正或短暂停顿时，语音层不必等整条“识别—推理—合成”链路结束才作反应。

这样的分工尤其适合需要边谈边办事的应用：前台保持对话，后台查资料或执行任务。官方给出的语音前端价格是每分钟 0.05 美元，后台模型与工具的开销还要另外计算。它也支持输出转写文本和显式轮次检测，便于已有系统接入。

OpenAI 报告其 Full Duplex Bench 相比 GPT-Realtime-2.1 提高 30 个百分点，语音任务评测还会搭配不同后台模型。应把“对话时机处理得更自然”和“后台任务完成得更好”分开看，不能都归功于语音模型。本文没有独立测试中文口音、嘈杂环境或电话场景的效果。

[GPT-Live-1 API 发布说明](https://openai.com/index/introducing-gpt-live-1-in-the-api/)

## 🤖 Show-Harness：给机器人一组模型看得懂的动作

机器人 / 论文与开源 · **8.5/10｜建议深挖**

这篇 9 月 9 日提交、9 月 10 日进入 HF 每日论文列表的研究，尝试把机器人动作变成视觉语言模型能直接选择的选项，例如向左移动一小步、下降、抓取和松开。与机器人对应的解释器，再把选项落实成幅度受限的实际动作。每走一步，模型重新接收相机画面和执行反馈。

它同时支持两种用法：调用前沿模型直接操作，或用少量示范微调小模型。研究者还提供 GUMI 图形界面，让人通过键盘和浏览器收集示范。论文、代码、训练流程及适配器文件均已可见；这种统一接口值得参考，因为它让示范采集、模型决策和机器人执行使用同一套动作表达。

实验以 Franka 和 AgileX 的单、双臂夹爪操作为主；基本测试包含十种物体与容器组合，每项通常十次试验，并设步数上限。作者报告的泛化优势还不能推广到人形机器人、灵巧手或复杂接触任务。它也不是“给任何机器人装个聊天模型就能干活”：相机、动作解释器和反馈规则仍是系统的一部分。

[论文正文](https://arxiv.org/html/2609.10522v1) · [代码](https://github.com/showlab/Show-Harness) · [模型适配器](https://huggingface.co/showlab/Show-Harness-VLMs)

## 🎮 补看：游戏规则交给程序，世界模型负责画面

世界模型 / 探索性论文 · **8/10｜持续观察**

Programmable World Model 的项目页于 9 月 5 日公开，论文于 9 月 9 日提交；这里补看的是新近完整论文，不当作昨天首次发布的项目。它针对一个熟悉的问题：生成的视频看起来连贯，但镜头一转，画面外的人物和已经发生的事件可能被“忘掉”。

作者让程序保存对象的位置、状态和交互规则，视频模型负责把这些状态画出来。自然语言先被 Agent 转成可执行规则；引擎维护世界状态，再用带状态的三维包围盒生成空间控制信号，交给视频生成器。角色离开镜头后仍存在，事件是否发生也有明确记录，画面不再独自承担全部记忆。

在作者自建的 50 段 CombatStateBench 测试中，数量准确率和状态准确率分别为 94% 和 98%。这两个指标由视觉语言模型判读，且状态指标只检查死亡事件后是否出现相应画面，不要求认出具体角色；对照模型使用的控制接口也不同。因此，结果说明显式状态控制有帮助，尚不能证明通用游戏模拟已经解决。仓库目前仍把推理代码与预训练权重列为未发布。

[论文正文](https://arxiv.org/html/2609.10540v1) · [项目与公开状态](https://github.com/AlayaLab/pwm)

## 本期主线

几项产品正在补齐 Agent 长期工作的具体条件：DeepSeek 减少读入与保存上下文的负担，Cursor 保存项目经验并协调任务，OpenAI 则把运行框架做成可调用的服务。之后评估 Agent，除了问它能答对什么，还要问同一个项目做完需要多少钱、中途失败如何继续、结果怎样验收。

两篇机器人与世界模型论文提供了另一种启发：把动作与状态表达清楚，有时比一味增加模型规模更有用。它们目前的实验范围都有限，但接口和状态管理的设计已经值得拆开研究。
